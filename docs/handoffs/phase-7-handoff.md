## Hard-won lessons (don't regress these)

1. **Follow-the-host follows ticking, not load/unload.** A forced room chunk keeps nearby chunks in memory without ticking them, so a machine there never gets `onChunkUnloaded` and would hold its room forever. `RoomTickets` reconciles once a second: a room is ticketed only while its machine passes `shouldTickBlocksAt`. Grid spacing is 4 chunks.
2. **A machine can't be placed inside its own room**, directly or through nesting (`RoomData.wouldNestInItself`); otherwise the room keeps itself loaded.
3. **Capability caches only notify after being queried**, and their invalidation listener must not query capabilities. So `CapabilityUpdates` defers invalidation plus `updateNeighborsAt` to the end of the tick, and nudges both ends when a machine loads, a tunnel loads, or any chunk next to a machine loads.
4. **Tunnels never buffer.**
   - A tunnel returns the far side's handler wrapped in a thin guard (`ProxyGuard`, max depth 8); the caller's transaction flows straight through.
   - A mapped face with nothing loaded or connected behind it returns an **empty handler, never null**, so pipes connect.
   - `null` only when there's no tunnel.
5. **The client needs "present but empty" answers.** Pipez re-checks extract sides on the client and drops the flag if a capability is `null`. On the client, providers answer an empty handler for machine faces that have a tunnel (block state booleans) and for a tunnel's inward side (the `INWARD` property). The server remains authoritative.
6. **Walls and machines aren't redstone conductors**, so chests open under them and power doesn't leak through. A future redstone tunnel must emit and read signals itself.
7. **Pipe → tunnel → pipe needs the far pipe set to extract.** That's Pipez's rule, not a bug: the tunnel keeps them as two networks.
8. **Tunnels are edited only by wrenches:** the Tunnel Wrench or anything tagged `c:tools/wrench`, via `PlayerInteractEvent.RightClickBlock`. Vanilla skips block use when sneaking with an item in hand.
9. **Always resolve the room level through `RoomDimension`** (`getRoomLevel`, `key`, `isRoomLevel`). On the GameTest server it's the overworld.
10. **Occupancy:** while a player is inside a room, its machine's chunk (and every machine up a nesting chain) is force-loaded by the `tinytunnels:occupancy` controller.

## Phase 7 scope (from the plan) and open decisions

| Item | Notes / decision needed |
|---|---|
| **Redstone tunnel** | **Decide: a separate redstone tunnel item (uses its own face), or an in/out setting on the existing tunnel.** Analysis so far: a face touches one block, so "items + redstone on one face" mostly helps inside the room (a machine fed items and switched by the signal). The separate item is simpler and clearer. Either way: signals are one-way (in or out) to avoid latch loops; push-based with the last value stored per end and re-applied on load; depth guard; the next tick, not immediate. The Tunnel Wrench is the natural place for mode or settings. |
| Tunnel settings screen | Only if tunnels get settings (redstone mode, typed toggles). The wrench would open it; a small menu plus one packet. |
| Typed or multiple tunnels per face | Players asked for this in Compact Machines (#108, #568). Depends on the redstone decision. |
| Mekanism chemicals | Optional dependency; Mekanism has no 26.1.2 release yet. |
| Jade tooltip | Machine: which faces have tunnels. Tunnel: which machine side it maps to. Jade is already a test mod. |
| Recipes and progression | Machines, Shrinker, Tunnel, Tunnel Wrench have none yet. |
| 2×2-chunk rooms | Geometry and allocation change; mind the 4-chunk spacing reasoning. |
| Living miniature | See `docs/research/platform-and-approach.md` (Tier 2). Start with a spike; 26.x render-state/submit; Vulkan arrives in 26.4. Every GPU buffer needs a deterministic free (Compact Machines' leak). |

**Also open, outside the phases** (`docs/todo.md`): room names, debug flag and command split, void safety.
