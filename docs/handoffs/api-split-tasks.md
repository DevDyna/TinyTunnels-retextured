# Tiny Tunnels API Split Tasks

The shared task list for the API split team (`api-split-team.md`). Started 2026-10-01.

**How to use it:**
- One row per task, named with its phase (`A2.3 ...`). Keep tasks small: one owner, a few files.
- **Claim** a task by putting your role in "Owner" and setting the status to `in progress`. Only edit your own rows; the lead adds and removes rows.
- **Status:** `open`, `in progress`, `blocked` (say on what, and message the lead), `review` (waiting on a QA run or the lead), `done`.
- **Done means:** it compiles, its tests pass in a QA run, its docs are updated, and the summary below says what changed, which files, and anything left (two to four lines).

**A3.12 (core):** cause: a block entity type mismatch, not the model data path. The world saved with Create has its machines under `kinetic_machine`. Without Create the server loads them as `MachineBlockEntity` typed `KINETIC_MACHINE` and sends that type, while the client builds its block entity from the block (`MachineBlock.newBlockEntity`, type `MACHINE`). The client drops any chunk or update tag whose type doesn't match (`LevelChunk.replaceWithPacketData`: `blockentity.getType() == type`; `ClientPacketListener.handleBlockEntityData`: `getBlockEntity(pos, packet.getType())`), so no faces ever arrive. The same would happen with Create for machines saved under `machine` (before Create). Fix: `MachineBlockEntity.getType()` always returns `MACHINE`, `KineticMachineBlockEntity.getType()` always `KINETIC_MACHINE` (what each block makes; NeoForge reads the type through `getType()` everywhere: save id, validity, packets, tickers). Such machines are resaved under the right id. A world saved without Create was never affected.
